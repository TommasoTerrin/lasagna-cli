# M3: Base Engine (runs, worktrees, flow, machine and human phases) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `lasagna start` creates a run with its own worktree and branch and drives a pipeline of `machine` and `human` phases to its end or to the next human wait, writing events as it goes. `decide`, `phase run`, `phase done`, `phase fail`, `cancel` and `clean` complete the lifecycle, and `status` also shows the `pending` phases.

**Architecture:** The scheduling rules live in a pure function (`flow.next_step`: pipeline + derived state in, next step out). Thin effectful modules do one thing each: `gitops` (git CLI), `definition` (read `.lasagna/` from a commit), `ids`, `resolve` (expressions), `runner` (processes), `outputs` (`$LASAGNA_OUTPUT`). The `engine` loops "derive state, ask `flow`, execute the step, append events" and returns an exit code; the Typer commands only parse arguments, take locks and call the engine. Current state always comes from replaying the log (M2).

**Tech Stack:** Python 3.11+, git CLI through `subprocess`, existing `FileLock`, `EventWriter`, `derive_state`, loader and validators. No new runtime dependency.

**Spec:** `harness/PROTOCOL.md` §3, §4, §6 (flow, decisions, expressions, outputs, environment), §7 (execution, exit codes, lifecycle), §8 (worktrees and commits), §9, §10 ("Avvio" rules), §11, `harness/START_PROMPT.md` (M3 scope), `config/primitives/*.schema.yaml`, `CLAUDE.md`, and the M2 plan for the modules it built.

**Status:** APPROVED by the user on 2026-11-20 (decisions 1-8 and the four interpretations; interpretation 2 in its corrected version). The decisions are recorded in the local `harness/PROTOCOL.md` (§1, §6, §8, §9, §11). Not started: Task 20 begins on the user's go.

## Approved decisions

START_PROMPT allows splitting a milestone but not merging two.

1. **Split M3 in two.** M3a (Tasks 20-28): engine core and `start`, enough to run a machine-only pipeline end to end. M3b (Tasks 29-33): human phases and the lifecycle commands (`decide`, `phase run/done/fail`, `cancel`, `clean`) plus `pending` rows in `status`. Two branches (`m3a-engine`, `m3b-human`), two PRs, a stop for review after each. (Approved as recommended.)
2. **Features not yet supported are refused at `start`.** Until M4 and M5, `start` exits 2 with a clear message for pipelines that use an agent actor, `loop`, `timeout`, `interactive`, or a sub-pipeline phase (checked on the pipeline and on every pipeline it references). One function in `start` holds the list, and each later milestone removes its entries. This keeps M3 shippable without half-implemented behaviour. The process runner and the process-tree kill are built in M3 (Ctrl+C needs them); wiring `timeout` is M4. (Approved as recommended.)
3. **How the `definition` commit is read** (approved, with a limit). `git archive --format=zip <commit> -- .lasagna`, **restricted to the `.lasagna/` folder of the commit**, extracted into a temporary folder; the existing `load_project` and `validate_project` then run on it unchanged. Nothing outside `.lasagna/` is ever extracted, and only committed content is read, never the working copy or the worktree. PROTOCOL §1 is updated accordingly (local file, in Italian).
4. **`--as` in M3, `--bind` in M4** (approved as recommended).
5. **Run ids** (approved, with a collision rule). `<pipeline>_<NN>`, the counter being per pipeline, at least two digits, assigned under a project lock `runs/.ids.lock`; no counter file. The highest `NN` is computed over **both** the logs in `runs/` **and** the existing local branches named `<branch_prefix><pipeline>_<NN>`, so that if logs are deleted a new id never collides with the branch of an earlier run. The log file of the new run reserves the id.
6. **Commit message of a phase** (approved as recommended): `lasagna(<run-id>): <full phase name>`.
7. **Ctrl+C in M3** (approved as recommended).
8. **New requirement (user, 2026-11-20): git local environment variables.** Lasagna must work on the right repository even when launched from a git hook (git exports `GIT_DIR`, `GIT_INDEX_FILE`, `GIT_WORK_TREE`, ... to hooks). The git wrapper of the engine, the repo root discovery and the environment of every phase command remove the variables listed by `git rev-parse --local-env-vars`, the same way the local pre-commit hook does. Covered by tests that simulate a hook launch (Tasks 20, 24, 27, 28). Recorded in PROTOCOL §6 and §8 (local file, in Italian).

## Global Constraints

- Everything committed is in English. Never `git add harness/`.
- User commands (`with.command`, `check`) run with `bash -c` on every OS through `shell.host_bash()`; `shell_env(sys.platform)` is added to every command environment. Values reach commands only as environment variables; `${{ }}` is never interpolated into a shell string.
- Lasagna's own git calls (`gitops`, `project.find_repo_root`) and every phase command run without the local git variables (`git rev-parse --local-env-vars`: `GIT_DIR`, `GIT_INDEX_FILE`, `GIT_WORK_TREE`, ...), so a launch from a git hook works on the repository of the working directory (decision 8).
- Before setting its own variables, Lasagna removes every inherited `LASAGNA_*` variable. `LASAGNA_WORKTREE`, `LASAGNA_OUTPUT`, `LASAGNA_STATE` are absolute; all paths use forward slashes.
- Only Lasagna writes `.lasagna/runs/*.jsonl`, through `EventWriter`, while holding the run lock. No background process: the command that advances a run drives it in the foreground until the next human wait or the end. Interactive terminal inheritance applies to `phase run`.
- Git through the `git` CLI via `subprocess`, no git library. Worktrees live in `worktrees.dir`, branches are `<branch_prefix><run-id>`. A phase ends with `git add -A` and `git commit --no-verify`, or no commit and `commit: null`.
- During a run, actors, pipelines and config are read from the `definition` commit, never from the working copy or the worktree.
- Exit codes (PROTOCOL §7): 0 ok (run `done`), 1 run failed, 2 usage or validation error, 3 waiting for a human, 130 Ctrl+C.
- Every command has a one-line docstring and every option and argument a `help` text.
- Tests never call Claude, OpenCode or the network. Machine commands in tests are plain bash. Git tests use real repositories in `tmp_path`, with a local identity. Tests must pass on Windows, Linux and macOS. Where a test needs a long-running or process-tree-spawning program, it is a Python script in `tests/fakes/` started through `sys.executable` (path passed with `to_bash_path`).
- Process-wide state that could leak between tests (cwd, environment) goes through `monkeypatch`. Inside the pre-commit hook the `GIT_*` variables are already unset; tests that spawn git must not rely on inherited ones.
- Workflow: the local pre-commit hook runs the full suite and both ruff checks, never bypass it with `--no-verify`. Never pipe test or lint commands; check their exit code. Commit messages are imperative English ending with the `Co-Authored-By` line from the session. Stop after Task 28 and after Task 33 for review.

### Task 26: flow rules (pure)

**Files:** Create `src/lasagna_cli/flow.py`, `tests/test_flow.py`.

**Interfaces:**
- Consumes: `Pipeline`, `RunState`, `PhaseState`.
- Produces (frozen dataclasses): `Execute(phase_id)`, `Prune(phase_id)`, `DecideRoute(phase_id)`, `Finish()`, and `next_step(pipeline: Pipeline, state: RunState) -> Step`. State is looked up by full name `<pipeline.name>/<id>`; a phase with no event is `pending`.

Rules (PROTOCOL §6 "Flusso", decision 2 of the M2 plan):
- A phase is concluded when `done`, `skipped` or `pruned`.
- A `pending` or `waiting` phase is eligible when all parents are concluded and at least one is not `pruned`; if all parents are `pruned` the step is `Prune(phase)`.
- A `done` phase with more than one child and no recorded `route` decision gives `DecideRoute(phase)`; once a `route` decision exists, every other direct child that is still `pending` gives `Prune(child)` (the chosen one is the decision `value`).
- A `skipped` phase with more than one child prunes all its direct children that are still `pending`.
- Only one phase runs at a time: if a phase is `running` or `waiting` (trigger), `next_step` returns that phase for `Execute`/trigger handling again (the engine decides what to do), and never a second one.
- `Finish` when every phase is concluded.
- A failed phase blocks everything (the engine never asks `flow` after `phase_failed`).

- [ ] **Step 1: Write the failing tests** on small pipelines built with `base_pipeline` and the loader (`load_project` on a `project`), with states built from `make_log` events through `derive_state`: linear start; second phase after the first is `done`; a join (`review` needs `quick-fix` and `tdd`) is eligible when one parent is `pruned` and the other `done`; all parents `pruned` gives `Prune`; route needed after a done phase with two children; after a route decision the other child gets `Prune` and then the chosen one `Execute`; a `skipped` phase with a route prunes its children; a `skipped` phase with a single child lets it run; `Finish` when all are concluded; propagation of pruning across a chain (`a` routes to `b`, `c`; `c` has child `d`; `d` needs only `c`): after `c` is pruned, `d` gets `Prune`; one-at-a-time: with `a` running no other step is returned.
- [ ] **Step 2: Run to make sure they fail.** **Step 3: Implement.** **Step 4: Tests, ruff, exit codes.**

### Task 27: engine, machine phases (no human, no triggers by humans)

**Files:** Create `src/lasagna_cli/engine.py`, `src/lasagna_cli/support.py`, `tests/test_engine_machine.py`.

**Interfaces:**
- Consumes: everything above, `EventWriter`, `derive_state`, `read_log`.
- Produces:
  - `support.unsupported_features(project: Project, pipeline: str) -> list[str]`: messages such as `phase 'x' of pipeline 'p': agent actors are not supported yet`, `... loop is not supported yet`, `... timeout ...`, `... interactive ...`, `... sub-pipelines ...`, following references recursively (decision 2).
  - `@dataclass class RunContext(root: Path, run_id: str, pipeline: Pipeline, project: Project, worktree: Path, inputs: dict[str, str], base_commit: str)`
  - `class Engine(ctx: RunContext, writer: EventWriter, *, runner=run_shell, platform=sys.platform)`; `Engine.drive() -> int` returns the exit code: 0 when `run_completed` `done` was written, 1 for a failed run, 3 when waiting (Task 29), 130 after an interruption.
- Phase lifecycle for `machine` actors, in this order (PROTOCOL §7 table, steps 1, 2, 3, 5, 7, 9, 10):
  1. Ask `flow.next_step`; `Prune` writes `phase_skipped` with reason `pruned`; `Finish` resolves the pipeline `outputs` (an unresolved one is omitted in a root run) and writes `run_completed` `done`.
  2. ## Interpretations (confirmed by the user, 2026-11-20)

1. **Phase names.** The `phase` field of events, commit messages and `LASAGNA_PHASE` is the full name `<pipeline>/<id>` (the fixtures already do this); command arguments accept the id or the full name (§11).
2. **Environment of decision `check`s.** Every `check` gets the standard `LASAGNA_*` variables. A `trigger` check gets no `LASAGNA_INPUT_*`, because a trigger is decided before the phase inputs are resolved (§6: `inputs.*` never in a trigger). A `route` check, and a `loop.until` check in M4, get the phase's already resolved `LASAGNA_INPUT_*`, because the phase has run (the acceptance pipeline's `until` check reads `$LASAGNA_INPUT_SPEC_DIR`). *This corrects my first draft, which said "minus the inputs" for all of them.*
3. **One `phase_waiting` per wait.** Running a command again while the same wait is open writes no second `phase_waiting`.
4. **Exit code 3** whenever the run stops for a human, including when a manual phase has just been opened.
